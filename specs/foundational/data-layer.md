# Foundational Spec — Data Layer (FROZEN CONTRACT)

Built in the foundational phase, then frozen. Workers consume this; they never modify it. If a
module needs a new entity or access pattern, the worker raises it to the supervisor, who amends
this spec and re-freezes — workers do not edit it directly.

## Single-table design
One DynamoDB table, on-demand, PITR on. Composite keys + GSIs. Entities and keys are defined in
the master spec (`spec/keirasjourney-spec.md`, "Data Model" + per-module entities). Summary of
key patterns:

- **PK** = `<ENTITY>#<id>`, **SK** = `DETAILS` (or sub-entity, e.g. `NOTE#<ts>`, `MESSAGE#<ts>`).
- **GSI1** (by date): `GSI1PK=ACTIVITIES`, `GSI1SK=<date>#<id>` (activities). Generalize per entity.
- **GSI2** (by category), **GSI3** (clinical by facility), **GSI4** (TEAS by date) per master spec.
- Singletons: `STUDENT_PROFILE/DETAILS`, `BUDGET/DETAILS`.

Every entity in the master spec MUST be representable here without a second table. If an access
pattern isn't covered by an existing key/GSI, add a GSI here (foundational phase only).

## Shared data-access library (the contract workers import)
Path: `backend/shared/data/`. Exports a typed client. Workers call these; they never write raw
DynamoDB calls in module code.

```ts
// One typed accessor per entity, e.g.:
activities.create(input): Promise<Activity>
activities.get(id): Promise<Activity | null>
activities.update(id, patch): Promise<Activity>
activities.delete(id): Promise<void>
activities.listByDate(range, opts): Promise<Activity[]>
activities.listByCategory(category, opts): Promise<Activity[]>
// ...mirrored for every entity: colleges, goals, courses, essays, scholarships,
// clinical, certifications, teas, interviews, whyNursing, contacts, touchpoints,
// visits, benchmarks, conversations, profile, budget.
```

Rules baked into the library:
- All timestamps ISO-8601 UTC; the lib stamps `createdAt`/`updatedAt`.
- IDs generated by the lib (uuid).
- **Visibility filtering is NOT done here** — it's enforced in the auth middleware/API layer off
  the caller's JWT (see `auth.md`), because the AI path needs unfiltered access when keira is the
  caller. The lib returns raw items; the API layer filters per requester.
- Idempotent hydration support: a `userEdited: string[]` field on hydratable entities; the lib
  exposes `mergePreservingUserEdits(id, aiData)`.

## Definition of done (foundational)
The table + all GSIs deployed (DataStack); the data-access lib implemented and unit-tested for
every entity's CRUD + list patterns; a fixture seeding helper for tests. Frozen and announced on
`.agent-bus/checkpoints/infra.md`.
